# Системные требования CaterFlow

**Версия:** 0.1
**Статус:** Черновик
**Дата:** 2026-11-13
**Основание:** Спецификация требований к ПО `docs/caterflow/srs.md`

## 1. Назначение документа

Документ определяет системные требования к программному продукту CaterFlow, разрабатываемому для автоматизации формирования меню, предварительного расчёта стоимости кейтеринговых услуг и обработки заявок клиентов.

В документе представлены функциональные и нефункциональные требования, их приоритеты, критерии приёмки и методы верификации. Также приведена матрица трассируемости, устанавливающая соответствие между системными требованиями и требованиями спецификации SRS.

Документ предназначен для использования заказчиком, разработчиками и участниками проверки программного продукта при проектировании, реализации и тестировании системы.

## 2. Шкала приоритетов

| Приоритет | Обозначение | Описание |
|:---------:|:-----------:|----------|
| 10 | Critical | Критически важное требование, без которого основная работа системы невозможна. |
| 20 | High | Важное требование, необходимое для полноценной работы системы. |
| 30 | Medium | Требование, повышающее удобство и эффективность использования системы. |
| 40 | Low | Требование с невысоким приоритетом, реализация которого может быть отложена. |
| 50 | Optional | Необязательное требование, реализуемое при наличии свободных ресурсов. |

## 3. Функциональные системные требования

### SYS-FUNC-001 — Управление данными каталога блюд

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна обеспечивать хранение и предоставление данных о блюдах, включая название, описание, состав, фотографию, категорию и стоимость. Для каждого блюда должна поддерживаться возможность определения его доступности для заказа.

#### Обоснование

Каталог является основой формирования меню клиентом. Актуальность информации о блюдах, их стоимости и доступности необходима для корректного оформления заказов и сокращения ручной работы сотрудников компании.

#### Критерии приёмки

- Каждое блюдо содержит название, описание, состав, категорию и стоимость.
- Для блюда может быть указана фотография.
- Система позволяет определить, доступно ли блюдо для добавления в заказ.
- Недоступные блюда не могут быть добавлены клиентом в меню.
- Изменения данных блюда отображаются в каталоге после сохранения.

#### Метод верификации

**Тестирование:** проверка создания, изменения и отображения данных блюд, а также проверки их доступности для заказа.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-002, REQ-FUNC-021, REQ-FUNC-022, REQ-FUNC-024.

### SYS-FUNC-002 — Просмотр и поиск блюд в каталоге

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна предоставлять клиентам возможность просматривать каталог доступных для заказа блюд, сгруппированных по категориям, и выполнять поиск блюд по названию.

#### Обоснование

Просмотр каталога позволяет клиентам самостоятельно знакомиться с ассортиментом компании и выбирать блюда для формирования меню. Поиск упрощает нахождение конкретных позиций при большом количестве предложений.

#### Критерии приёмки

- Каталог отображает доступные для заказа блюда.
- Блюда сгруппированы по категориям.
- Для каждой позиции отображаются название, описание, состав, фотография (при наличии) и стоимость.
- Клиент может выбрать категорию для просмотра соответствующих блюд.
- Поиск выполняется по названию блюда.
- При отсутствии совпадений система отображает соответствующее сообщение.
- Недоступные для заказа блюда не отображаются среди доступных позиций.

#### Метод верификации

**Тестирование:** проверка отображения каталога, переключения категорий и поиска блюд по различным поисковым запросам.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-001, REQ-FUNC-002, REQ-FUNC-003.

### SYS-FUNC-003 — Использование готовых наборов блюд

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна предоставлять клиентам возможность просматривать готовые наборы блюд, добавлять выбранный набор в формируемое меню и изменять его состав до оформления заявки.

#### Обоснование

Готовые наборы упрощают процесс выбора блюд и сокращают время формирования заказа. Возможность изменения состава позволяет адаптировать предложение под количество гостей и предпочтения клиента.

#### Критерии приёмки

- Система отображает список доступных готовых наборов.
- Для каждого набора отображаются название, описание, состав и стоимость.
- Клиент может добавить выбранный набор в формируемое меню.
- Клиент может удалить отдельные блюда из набора.
- Клиент может добавить в набор другие доступные блюда.
- При изменении состава набора стоимость меню пересчитывается.

#### Метод верификации

**Тестирование:** проверка отображения готовых наборов, добавления набора в меню, изменения его состава и перерасчёта стоимости.

#### Дополнительная информация

- **Приоритет:** 20 — High.
- **Связанные требования SRS:** REQ-FUNC-005, REQ-FUNC-004, REQ-FUNC-008.

### SYS-FUNC-004 — Формирование индивидуального меню

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна обеспечивать формирование индивидуального меню путём добавления доступных блюд из каталога, удаления выбранных позиций и изменения количества порций для каждого блюда.

#### Обоснование

Самостоятельное формирование меню позволяет клиентам адаптировать заказ под формат мероприятия, количество гостей и индивидуальные предпочтения. Это сокращает необходимость ручного подбора блюд менеджером.

#### Критерии приёмки

- Клиент может добавить доступное блюдо в формируемое меню.
- Клиент может удалить ранее добавленное блюдо.
- Для каждой позиции можно указать количество порций.
- Система отображает текущий состав меню и количество порций каждого блюда.
- Система не позволяет добавить недоступное для заказа блюдо.
- Изменения состава меню сохраняются в течение текущего сеанса оформления заказа.

#### Метод верификации

**Тестирование:** проверка добавления и удаления блюд, изменения количества порций и отображения актуального состава меню.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-004, REQ-FUNC-007.

### SYS-FUNC-005 — Рекомендация количества порций

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна автоматически рассчитывать рекомендуемое количество порций для выбранных блюд на основании указанного клиентом количества гостей.

#### Обоснование

Автоматическая рекомендация помогает клиенту определить необходимое количество еды для мероприятия и упрощает формирование заказа. При этом клиент должен сохранять возможность самостоятельно корректировать предложенные значения.

#### Критерии приёмки

- Клиент может указать количество гостей мероприятия.
- После указания количества гостей система рассчитывает рекомендуемое количество порций для выбранных блюд.
- Результаты расчёта отображаются в конструкторе меню.
- Клиент может изменить рекомендованное количество порций.
- При изменении количества гостей система обновляет рекомендации.
- Рекомендации не заменяют выбранные клиентом значения без его согласия.

#### Метод верификации

**Тестирование:** проверка расчёта рекомендаций при различных значениях количества гостей, а также проверка возможности ручного изменения предложенного количества порций.

#### Дополнительная информация

- **Приоритет:** 20 — High.
- **Связанные требования SRS:** REQ-FUNC-006, REQ-FUNC-004.
- **Примечание:** конкретные правила расчёта количества порций должны быть определены при проектировании системы и согласованы с заказчиком.

### SYS-FUNC-006 — Контроль минимального количества порций

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна обеспечивать установку и проверку минимального количества порций для отдельных блюд при формировании клиентом меню.

#### Обоснование

Для некоторых блюд приготовление меньшего количества порций может быть экономически нецелесообразным или технологически невозможным. Проверка минимального количества позволяет исключить некорректные позиции из заказа до его оформления.

#### Критерии приёмки

- Для каждого блюда может быть задано минимальное количество порций.
- При добавлении блюда система учитывает установленное минимальное количество.
- Система не позволяет указать количество порций ниже установленного минимума.
- При попытке указать меньшее количество система отображает сообщение с указанием минимального значения.
- Для блюд без установленного ограничения применяется стандартное правило формирования количества порций.

#### Метод верификации

**Тестирование:** проверка добавления блюд с установленным минимальным количеством порций, изменения количества и обработки попыток указать значение ниже допустимого.

#### Дополнительная информация

- **Приоритет:** 20 — High.
- **Связанные требования SRS:** REQ-FUNC-007, REQ-FUNC-004.

### SYS-FUNC-007 — Расчёт стоимости блюд

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна автоматически рассчитывать стоимость каждой позиции меню на основании установленной цены блюда и выбранного количества порций, а также определять суммарную стоимость всех блюд в меню.

#### Обоснование

Автоматический расчёт исключает необходимость ручного подсчёта стоимости заказа менеджером и позволяет клиенту видеть финансовые последствия изменения состава меню.

#### Критерии приёмки

- Стоимость позиции рассчитывается как произведение цены одной порции на количество порций.
- Суммарная стоимость блюд определяется как сумма стоимости всех позиций меню.
- При добавлении или удалении блюда стоимость меню пересчитывается.
- При изменении количества порций стоимость соответствующей позиции и всего меню обновляется.
- При изменении цены блюда система использует актуальную цену для новых расчётов.
- Стоимость отображается в денежном формате с двумя знаками после запятой.

#### Метод верификации

**Тестирование:** проверка расчёта стоимости отдельных позиций и всего меню, включая сценарии изменения состава, количества порций и цен блюд.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-008, REQ-FUNC-010.

### SYS-FUNC-008 — Расчёт стоимости доставки

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна определять стоимость доставки на основании указанного клиентом адреса мероприятия и соответствующего ему тарифа доставки.

#### Обоснование

Автоматический расчёт стоимости доставки позволяет заранее учитывать транспортные расходы в общей стоимости заказа и избавляет менеджеров от необходимости рассчитывать их вручную.

#### Критерии приёмки

- Клиент может указать адрес доставки при оформлении заказа.
- Система определяет тарифную зону, к которой относится указанный адрес.
- Для каждой тарифной зоны предусмотрена фиксированная стоимость доставки.
- Стоимость доставки отображается отдельно от стоимости блюд.
- Если адрес не относится ни к одной обслуживаемой зоне, система сообщает клиенту о невозможности доставки по указанному адресу.
- При изменении адреса стоимость доставки пересчитывается.

#### Метод верификации

**Тестирование:** проверка определения тарифной зоны и расчёта стоимости доставки для адресов из разных зон, а также обработка адресов за пределами обслуживаемой территории.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-009, REQ-FUNC-010.
- **Примечание:** перечень тарифных зон и соответствующие им стоимости предоставляются заказчиком.

### SYS-FUNC-009 — Расчёт общей стоимости заказа

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна автоматически определять общую предварительную стоимость заказа как сумму стоимости выбранных блюд и стоимости доставки.

#### Обоснование

Отображение общей стоимости позволяет клиенту оценить расходы до отправки заявки и принять решение об оформлении заказа.

#### Критерии приёмки

- Общая стоимость рассчитывается на основании актуальной стоимости блюд и доставки.
- Стоимость блюд и стоимость доставки отображаются отдельными составляющими.
- Общая предварительная стоимость отображается отдельно от составляющих.
- При изменении состава меню, количества порций или адреса доставки общая стоимость пересчитывается.
- При отсутствии возможности доставки система не рассчитывает итоговую стоимость с учётом доставки.

#### Метод верификации

**Тестирование:** проверка общей стоимости при различных составах меню, количестве порций и тарифах доставки, включая изменение параметров заказа.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-008, REQ-FUNC-009, REQ-FUNC-010.

### SYS-FUNC-010 — Оформление заявки без регистрации

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна предоставлять незарегистрированным клиентам возможность оформить заявку на кейтеринг путём заполнения формы с контактными данными, параметрами мероприятия и сформированным меню.

#### Обоснование

Возможность оформления заявки без регистрации снижает количество действий со стороны клиента и упрощает привлечение новых заказчиков.

#### Критерии приёмки

- Незарегистрированный клиент может перейти к оформлению заявки из конструктора меню.
- Форма содержит поля для ввода имени, адреса электронной почты, номера телефона и адреса мероприятия.
- Форма позволяет указать дату и время мероприятия, а также его тип.
- Система проверяет заполнение обязательных полей.
- Система проверяет корректность формата электронной почты и номера телефона.
- Перед отправкой заявки клиенту отображаются состав меню и предварительная стоимость заказа.
- После успешной отправки заявки система отображает подтверждение её приёма.

#### Метод верификации

**Тестирование:** проверка оформления заявки без авторизации, заполнения обязательных полей, валидации контактных данных и обработки успешной отправки.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-011, REQ-FUNC-012, REQ-FUNC-013.

### SYS-FUNC-011 — Регистрация и передача заявки на обработку

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна сохранять успешно отправленные клиентами заявки вместе с контактными данными, параметрами мероприятия, составом меню и предварительной стоимостью, а также предоставлять менеджерам доступ к зарегистрированным заявкам для дальнейшей обработки.

#### Обоснование

Централизованное хранение заявок позволяет менеджерам получать информацию о новых заказах в едином интерфейсе, снижает риск потери обращений и упрощает контроль процесса их обработки.

#### Критерии приёмки

- После успешной отправки заявки система сохраняет все введённые клиентом данные.
- Каждой заявке присваивается уникальный идентификатор.
- Сохранённая заявка получает статус «Новая заявка».
- Заявка содержит контактные данные клиента, параметры мероприятия, состав меню и предварительную стоимость.
- Менеджер может просматривать зарегистрированные заявки в панели управления.
- При возникновении ошибки сохранения система сообщает клиенту о невозможности отправки заявки.
- Повторная отправка формы после ошибки не должна приводить к созданию дублирующей заявки при условии, что первая заявка уже была сохранена.

#### Метод верификации

**Тестирование:** проверка сохранения заявок, присвоения уникальных идентификаторов, начального статуса, отображения заявок в панели менеджера и обработки ошибок сохранения.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-FUNC-013, REQ-FUNC-017, REQ-REL-001, REQ-REL-002.

### SYS-FUNC-012 — Регистрация и авторизация клиентов

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна предоставлять клиентам возможность создавать учётные записи, выполнять вход в личный кабинет и завершать текущий сеанс авторизации.

#### Обоснование

Учётные записи позволяют связывать заказы с конкретными клиентами, предоставлять доступ к истории заказов и сохранять индивидуальные варианты меню.

#### Критерии приёмки

- Клиент может зарегистрировать учётную запись с использованием предусмотренных системой регистрационных данных.

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна предоставлять менеджеру возможность сформировать и скачать заявку в формате PDF. Документ должен содержать номер заявки, контактные данные клиента, сведения о мероприятии, состав меню, количество порций и предварительную стоимость.

#### Обоснование

Выгрузка заявки в PDF позволяет менеджеру сохранять сведения о заказе, использовать их при подготовке мероприятия и при необходимости распечатывать документ.

#### Критерии приёмки

- Менеджер может сформировать PDF-документ для выбранной заявки.
- Документ содержит номер заявки и основные сведения о клиенте и мероприятии.
- В документе отображаются состав меню, количество порций и предварительная стоимость.
- Сформированный PDF-файл открывается и корректно отображает содержащиеся в нём данные.
- Пользователь без прав менеджера не может воспользоваться функцией выгрузки.

#### Метод верификации

**Тестирование:** проверка формирования и скачивания PDF-файла, полноты содержащихся в нём данных и ограничения доступа к функции.

#### Дополнительная информация

- **Приоритет:** 20 — High.
- **Связанные требования SRS:** REQ-FUNC-028, REQ-SEC-001.

**Тестирование:** измерение времени загрузки основных страниц приложения в условиях, соответствующих предполагаемой эксплуатации.

### SYS-NF-002 — Скорость выполнения расчётов

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Система должна выполнять перерасчёт стоимости меню и доставки не более чем за 2 секунды после изменения параметров заказа.

Быстрый перерасчёт необходим для обеспечения непрерывного взаимодействия клиента с конструктором меню и своевременного отображения актуальной стоимости заказа.

- После изменения адреса доставки система обновляет стоимость доставки и общую стоимость не более чем за 2 секунды.

**Тестирование:** измерение времени выполнения перерасчётов при изменении различных параметров заказа.

- Администратор имеет доступ к функциям управления каталогом и готовыми наборами.

**Тестирование:** проверка доступа к функциям приложения под каждой предусмотренной ролью, включая попытки обращения к закрытым разделам.

- Введённые клиентом данные сохраняются в форме при обнаружении ошибки валидации.

**Тестирование:** проверка обработки пустых и некорректных полей, а также моделирование ошибок при отправке заявки.

#### Метод верификации

**Тестирование и демонстрация:** проверка отображения и работы основных страниц на устройствах с различными размерами экранов.

### SYS-NF-015 — Соблюдение сроков разработки первой версии

**Статус:** Черновик  
**Дата:** 2026-11-13

#### Формулировка

Разработка и подготовка первой версии системы к передаче заказчику должны быть выполнены в пределах согласованного трёхмесячного срока.

#### Обоснование

Ограничение срока разработки связано с необходимостью подготовить систему к сезону корпоративных мероприятий и начать её использование компанией в запланированный период.

#### Критерии приёмки

- Для разработки составлен календарный план с распределением работ по итерациям.
- Для каждой итерации определены сроки и перечень реализуемых функций.
- Выполнение работ контролируется относительно утверждённого плана.
- Первая версия системы подготовлена к передаче заказчику в пределах согласованного срока либо изменения сроков предварительно согласованы сторонами.

#### Метод верификации

**Анализ:** сравнение фактических сроков выполнения работ с утверждённым календарным планом.

#### Дополнительная информация

- **Приоритет:** 10 — Critical.
- **Связанные требования SRS:** REQ-DEAD-001.
- **Примечание:** конкретная дата завершения разработки определяется после согласования календарного плана с заказчиком.
