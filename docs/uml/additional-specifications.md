# Дополнительные спецификации проекта CaterFlow

## 1. Назначение и границы системы

CaterFlow представляет собой веб-приложение для автоматизации формирования и обработки заявок на организацию кейтерингового обслуживания. Система предназначена для использования клиентами и сотрудниками кейтеринговой компании.

Основное назначение системы заключается в предоставлении клиентам инструментов для просмотра каталога блюд, формирования меню, расчёта предварительной стоимости и оформления заявок. Сотрудникам компании предоставляются средства для обработки поступивших заявок и управления информационным наполнением каталога.

В рамках рассматриваемой модели выделяются следующие функциональные области:

- просмотр и поиск позиций каталога;
- регистрация и авторизация пользователей;
- формирование и редактирование меню;
- расчёт стоимости меню и доставки;
- оформление заявок клиентами и просмотр поступивших заявок сотрудниками;
- обработка заявок менеджерами;
- управление каталогом блюд администратором.

Система рассматривается как единое веб-приложение с централизованным хранением данных.

## 2. Актёры и разграничение доступа

В системе предусмотрены четыре основные пользовательские роли.

| Актёр | Основные полномочия |
|---|---|
| Гость | Просмотр и поиск блюд, формирование меню, расчёт стоимости, оформление заявки без регистрации, регистрация учётной записи. |
| Клиент | Все доступные функции гостя и авторизация. |
| Менеджер | Авторизация, просмотр и фильтрация поступивших заявок, получение подробной информации о них, редактирование состава и изменение статусов заявок. |
| Администратор | Авторизация, управление блюдами, категориями, готовыми наборами, ценами и доступностью позиций каталога. |
Доступ к операциям определяется ролью авторизованного пользователя. Клиент не должен получать доступ к заявкам других клиентов, а операции управления каталогом и обработки заявок должны быть доступны только соответствующим категориям сотрудников.

## 3. Бизнес-правила обработки заявок

Для регистрации и обработки заявок устанавливаются следующие правила:

1. Оформление заявки доступно гостю без регистрации и авторизованному клиенту.
2. Заявка должна содержать сведения о клиенте, параметрах мероприятия и выбранном меню.
3. Перед регистрацией заявки система проверяет полноту и корректность обязательных данных.
4. После успешной регистрации заявке автоматически присваивается начальный статус «Новая заявка».
5. Изменение статуса выполняется менеджером в соответствии с допустимыми переходами.
6. Каждое изменение статуса должно сохраняться в базе данных.
7. Менеджер имеет возможность просматривать и обрабатывать поступившие заявки.

В рамках модели жизненный цикл заявки включает следующие состояния:

- «Новая заявка» — заявка зарегистрирована в системе и ожидает рассмотрения;
- «В обработке» — менеджер приступил к рассмотрению заявки;
- «Подтверждена» — заявка согласована;
- «Выполнена» — обслуживание по заявке завершено;
- «Отменена» — дальнейшая обработка заявки прекращена.

Допустимость переходов между состояниями должна контролироваться системой. Завершённые и отменённые заявки не должны возвращаться к обычным этапам обработки без специально предусмотренного бизнес-правила.

## 4. Правила формирования меню

Формирование меню выполняется клиентом на основании информации, представленной в каталоге.

При работе с меню применяются следующие правила:

1. В меню могут включаться только доступные для выбора позиции каталога.
2. Для каждой позиции указывается количество.
3. Клиент может добавлять новые блюда, удалять ранее выбранные позиции и изменять их количество.
4. Система должна отображать актуальный состав меню после внесения изменений.

Готовые наборы рассматриваются как заранее сформированные комбинации блюд, которые могут использоваться клиентом при создании собственного меню.

## 5. Правила расчёта стоимости

Расчёт стоимости выполняется на основании состава сформированного меню, количества выбранных позиций и установленных условий доставки.

При расчёте система должна учитывать:

- стоимость каждой выбранной позиции;
- количество единиц каждой позиции;
- общую стоимость выбранных блюд;
- стоимость доставки, определяемую по установленным условиям;
- итоговую предварительную стоимость заказа.

Изменение состава меню или количества позиций должно приводить к обновлению расчётных значений.

Если для выполнения расчёта отсутствуют обязательные параметры, система должна запросить их у клиента. Если выбранная позиция становится недоступной, система должна уведомить пользователя о необходимости скорректировать меню.

Отображаемая стоимость является предварительной и используется клиентом для ознакомления с предполагаемыми затратами до оформления заявки.

## 6. Требования к данным и их хранению

Система должна обеспечивать централизованное хранение информации, необходимой для выполнения основных бизнес-процессов.

К основным группам данных относятся:

- учётные записи пользователей и сведения об их ролях;
- категории и позиции каталога;
- готовые наборы блюд;
- состав сформированных меню;
- сведения о мероприятиях;
- зарегистрированные заявки;
- текущие статусы заявок.

Связи между данными должны обеспечивать целостность информации. В частности, заявки должны быть связаны с создавшими их клиентами, а позиции меню — с соответствующими блюдами каталога.

Доступ к данным должен осуществляться с учётом полномочий пользователя.

## 7. Ограничения и допущения

При проектировании динамической модели принимаются следующие ограничения и допущения:

1. Система реализуется в виде веб-приложения, взаимодействие с которым осуществляется через браузер.
2. Серверная часть отвечает за обработку запросов, выполнение бизнес-правил и взаимодействие с базой данных.
3. В качестве основной СУБД используется PostgreSQL.
4. Серверная часть разрабатывается на Java с использованием Spring Boot.
5. Управление данными осуществляется с применением средств Spring Data JPA.
6. Для сборки проекта и управления зависимостями используется Maven.
7. Для доступа к функциям, требующим авторизации, пользователь должен иметь соответствующую учётную запись.
8. Расчёт стоимости выполняется на основании данных каталога и заданных правил, без подключения внешних платёжных сервисов.
9. В рамках рассматриваемой модели основное внимание уделяется формированию и обработке заявок, а не организации фактической доставки или приготовления блюд.
10. История ранее оформленных заказов не рассматривается как самостоятельная функция первой версии системы.

## 8. Общие требования к поведению системы

При взаимодействии с пользователями система должна соблюдать следующие принципы:

- проверять корректность входных данных перед выполнением операций;
- предоставлять понятные сообщения об ошибках и результатах действий;
- не допускать выполнения операций пользователями без соответствующих полномочий;
- сохранять изменения данных после успешного выполнения операций;
- обеспечивать согласованность информации между связанными функциональными областями;
- информировать пользователя о невозможности выполнения операции, если нарушены установленные условия.

Указанные положения используются при разработке вариантов использования, диаграмм активности, состояний и последовательности.
