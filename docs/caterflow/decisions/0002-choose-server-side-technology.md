# Выбор серверной технологии для CaterFlow

## Контекст и постановка задачи

Серверная часть CaterFlow должна обрабатывать HTTP-запросы, выполнять бизнес-логику, взаимодействовать с базой данных и обеспечивать работу пользовательских и административных функций.

В качестве основного языка программирования проекта определён C++. Необходимо выбрать способ разработки серверной части, который позволит реализовать требуемую функциональность в рамках ограниченного срока проекта и упростит дальнейшее сопровождение приложения.

Какую технологию следует использовать для реализации серверной части CaterFlow?

## Драйверы решения

* Соответствие выбранной технологии языку программирования C++.
* Возможность обработки HTTP-запросов и организации маршрутизации.
* Возможность взаимодействия с PostgreSQL.
* Простота разработки и сопровождения серверной части.
* Наличие документации и доступность необходимых библиотек.
* Возможность реализации проекта в течение ориентировочно трёх месяцев (REQ-DEAD-001).
* Поддержка требований к производительности и развёртыванию (REQ-PERF-001, REQ-PERF-002, REQ-INST-001).

## Рассмотренные варианты

* C++ с веб-фреймворком Drogon.
* C++ с веб-фреймворком Crow.
* Самостоятельная реализация обработки HTTP-запросов без специализированного веб-фреймворка.

## Итог решения

Выбранный вариант: «C++ с веб-фреймворком Drogon».

Предлагается использовать Drogon, поскольку он предоставляет готовые средства для создания HTTP-маршрутов, обработки запросов и взаимодействия с базой данных. Это позволяет сократить объём низкоуровневой разработки и сосредоточиться на реализации бизнес-функций CaterFlow.

Решение имеет предварительный статус и подлежит согласованию с заказчиком и проверке совместимости с выбранной средой разработки.

### Последствия

* Хорошо, потому что использование готового веб-фреймворка сокращает объём самостоятельно разрабатываемого серверного кода.
* Хорошо, потому что упрощается организация маршрутизации и обработка HTTP-запросов.
* Хорошо, потому что готовые механизмы фреймворка позволяют сосредоточиться на бизнес-логике приложения.
* Нейтрально, потому что разработчикам необходимо изучить особенности Drogon и его инструменты.
* Плохо, потому что разработка будет зависеть от возможностей и ограничений выбранного фреймворка.
* Плохо, потому что потребуется проверить совместимость Drogon, PostgreSQL и инструментов сборки в используемой среде разработки.

### Подтверждение

Соблюдение решения проверяется в ходе реализации серверной части и код-ревью.

Необходимо убедиться, что:

* HTTP-запросы обрабатываются средствами Drogon.
* Маршруты серверной части организованы с использованием механизмов фреймворка.
* Приложение может взаимодействовать с PostgreSQL.
* Серверная часть успешно собирается и запускается в целевой среде.
* Основные операции соответствуют требованиям производительности, указанным в SRS.

## Плюсы и минусы вариантов

### C++ с веб-фреймворком Drogon

* Хорошо, потому что предоставляет готовые средства маршрутизации HTTP-запросов.
* Хорошо, потому что поддерживает асинхронную обработку запросов.
* Хорошо, потому что предоставляет инструменты для взаимодействия с базами данных.
* Хорошо, потому что позволяет сократить объём низкоуровневой разработки.
* Нейтрально, потому что требует изучения документации и особенностей фреймворка.
* Плохо, потому что накладывает зависимость от выбранного инструментария и его совместимости с окружением проекта.

### C++ с веб-фреймворком Crow

* Хорошо, потому что предоставляет средства создания HTTP-маршрутов и обработки запросов.
* Хорошо, потому что имеет относительно простой интерфейс для разработки небольших веб-приложений.
* Нейтрально, потому что для взаимодействия с PostgreSQL потребуется отдельно выбрать и настроить соответствующие средства.
* Плохо, потому что часть задач интеграции и организации серверной логики потребуется реализовать самостоятельно.
* Плохо, потому что возможности готовых компонентов для решения задач проекта необходимо дополнительно проверять.

### Самостоятельная реализация обработки HTTP-запросов

* Хорошо, потому что разработчик получает полный контроль над внутренней реализацией серверной части.
* Хорошо, потому что отсутствует зависимость от конкретного веб-фреймворка.
* Плохо, потому что потребуется самостоятельно реализовать маршрутизацию, обработку запросов и другие базовые механизмы.
* Плохо, потому что увеличивается объём кода и время разработки.
* Плохо, потому что повышается риск ошибок при реализации сетевого взаимодействия и обработки запросов.
* Плохо, потому что данный подход не соответствует ограниченному сроку разработки CaterFlow.
