# Выбор PostgreSQL в качестве системы управления базами данных

## Контекст и постановка задачи

CaterFlow должна хранить сведения о клиентах, сотрудниках, блюдах, категориях, готовых наборах, меню и заявках. Данные связаны между собой, поэтому система должна обеспечивать их целостность и надёжное хранение.

Необходимо выбрать систему управления базами данных, которая подходит для работы веб-приложения, поддерживает структурированные данные и обеспечивает выполнение операций с информацией в условиях одновременной работы нескольких пользователей.

Какую СУБД следует использовать для постоянного хранения данных CaterFlow?

## Драйверы решения

* Поддержка реляционной модели данных и связей между сущностями.
* Обеспечение целостности хранимой информации.
* Поддержка транзакций при выполнении операций с заявками, меню и каталогом.
* Возможность одновременной работы нескольких пользователей.
* Совместимость с выбранной серверной технологией C++ и веб-фреймворком Drogon.
* Возможность развёртывания и сопровождения базы данных.
* Соответствие требованиям надёжного сохранения заявок (REQ-REL-001) и обработки ошибок (REQ-REL-002).

## Рассмотренные варианты

* PostgreSQL.
* SQLite.
* MongoDB.

## Итог решения

Выбранный вариант: «PostgreSQL».

Предлагается использовать PostgreSQL в качестве основной системы управления базами данных. Реляционная модель подходит для хранения структурированной информации и организации связей между клиентами, сотрудниками, блюдами, меню и заявками.

PostgreSQL предоставляет механизмы транзакций, ограничения целостности и управления доступом к данным. Это соответствует требованиям CaterFlow к надёжности хранения информации и обработке пользовательских операций.

Решение имеет предварительный статус и подлежит согласованию с заказчиком, а также проверке совместимости с выбранной серверной технологией.

### Последствия

* Хорошо, потому что реляционная модель позволяет организовать структурированное хранение данных и связи между сущностями.
* Хорошо, потому что транзакции помогают обеспечивать согласованность данных при выполнении операций.
* Хорошо, потому что PostgreSQL поддерживает одновременную работу нескольких пользователей.
* Хорошо, потому что СУБД предоставляет механизмы ограничения целостности и управления доступом.
* Нейтрально, потому что для развёртывания потребуется отдельный сервер базы данных или соответствующая серверная служба.
* Плохо, потому что настройка и сопровождение PostgreSQL требуют дополнительных административных действий по сравнению с SQLite.

### Подтверждение

Соблюдение решения проверяется при реализации слоя доступа к данным и проведении функционального тестирования.

Необходимо убедиться, что:

* Приложение успешно устанавливает соединение с PostgreSQL.
* Структура базы данных соответствует основным сущностям системы.
* Связи между таблицами обеспечивают целостность данных.
* Операции создания, изменения и получения записей выполняются корректно.
* Сохранение заявок соответствует требованиям надёжности.
* При ошибках выполнения операций данные не переходят в некорректное состояние.

## Плюсы и минусы вариантов

### PostgreSQL

* Хорошо, потому что поддерживает реляционную модель и сложные связи между таблицами.
* Хорошо, потому что предоставляет транзакции и механизмы обеспечения целостности данных.
* Хорошо, потому что подходит для многопользовательских веб-приложений.
* Хорошо, потому что предоставляет развитые средства управления доступом и резервного копирования.
* Нейтрально, потому что требует отдельной настройки и сопровождения серверной СУБД.
* Плохо, потому что по сравнению с SQLite требует больше ресурсов и инфраструктурной настройки.

### SQLite

* Хорошо, потому что не требует отдельного сервера базы данных.
* Хорошо, потому что отличается простотой настройки и использования.
* Хорошо, потому что подходит для небольших локальных приложений и прототипов.
* Плохо, потому что имеет ограничения при одновременном выполнении операций записи несколькими пользователями.
* Плохо, потому что менее удобна для централизованной работы многопользовательского веб-приложения в предполагаемом сценарии эксплуатации.

### MongoDB

* Хорошо, потому что поддерживает гибкую структуру документов.
* Хорошо, потому что позволяет хранить данные без обязательного предварительного определения жёсткой схемы.
* Нейтрально, потому что может использоваться для хранения отдельных типов неструктурированной информации.
* Плохо, потому что основная структура данных CaterFlow предполагает большое количество взаимосвязанных сущностей.
* Плохо, потому что использование документной модели не даёт существенных преимуществ для текущих задач проекта.
* Плохо, потому что потребуется учитывать особенности организации связей и обеспечения целостности данных.
