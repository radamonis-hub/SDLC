# Выбор серверной технологии для CaterFlow

## Контекст и постановка задачи

Серверная часть CaterFlow должна обрабатывать HTTP-запросы, выполнять бизнес-логику, взаимодействовать с базой данных и обеспечивать работу пользовательских и административных функций.

В качестве основного языка программирования проекта определена Java. Необходимо выбрать технологию разработки серверной части, которая позволит реализовать требуемую функциональность в рамках ограниченного срока проекта и упростит дальнейшее сопровождение приложения.

Какую технологию следует использовать для реализации серверной части CaterFlow?

## Драйверы решения

* Соответствие выбранной технологии языку программирования Java.
* Возможность обработки HTTP-запросов и организации маршрутизации.
* Возможность взаимодействия с PostgreSQL.
* Простота разработки и сопровождения серверной части.
* Наличие документации и доступность необходимых библиотек.
* Возможность реализации проекта в течение ориентировочно трёх месяцев (REQ-DEAD-001).
* Поддержка требований к производительности и развёртыванию (REQ-PERF-001, REQ-PERF-002, REQ-INST-001).

## Рассмотренные варианты

* Java 21 с фреймворком Spring Boot.
* Java с платформой Jakarta EE.
* Самостоятельная реализация обработки HTTP-запросов без специализированного веб-фреймворка.

## Итог решения

Выбранный вариант: «Java 21 с фреймворком Spring Boot».

Предлагается использовать Spring Boot, поскольку он предоставляет готовые средства для создания REST API, обработки HTTP-запросов, организации маршрутизации и взаимодействия с базой данных. Фреймворк также упрощает конфигурирование приложения и интеграцию необходимых библиотек.

Для управления зависимостями и сборки проекта предлагается использовать Maven. Взаимодействие с PostgreSQL будет организовано с применением Spring Data JPA и JDBC-драйвера PostgreSQL.

Выбранный стек позволит сократить объём вспомогательного кода и сосредоточиться на реализации бизнес-функций CaterFlow.

Решение имеет предварительный статус и подлежит согласованию с заказчиком и проверке совместимости с выбранной средой разработки.

### Последствия

* Хорошо, потому что Spring Boot предоставляет готовые средства для создания REST API и обработки HTTP-запросов.
* Хорошо, потому что интеграция с PostgreSQL упрощается благодаря доступным инструментам Java и Spring.
* Хорошо, потому что автоматическая конфигурация и готовые компоненты сокращают объём вспомогательного кода.
* Хорошо, потому что Maven упрощает управление зависимостями и сборку приложения.
* Нейтрально, потому что разработчикам необходимо изучить особенности Spring Boot и используемых библиотек.
* Плохо, потому что разработка будет зависеть от возможностей и ограничений выбранного фреймворка.
* Плохо, потому что необходимо учитывать потребление памяти и время запуска приложения при настройке и развёртывании.

### Подтверждение

Соблюдение решения проверяется в ходе реализации серверной части и код-ревью.

Необходимо убедиться, что:

* HTTP-запросы обрабатываются средствами Spring Boot.
* Маршруты серверной части организованы с использованием механизмов Spring MVC.
* Серверная часть предоставляет REST API для взаимодействия с клиентской частью.
* Приложение может взаимодействовать с PostgreSQL.
* Проект успешно собирается с использованием Maven и запускается в целевой среде.
* Основные операции соответствуют требованиям производительности, указанным в SRS.

## Плюсы и минусы вариантов

### Java 21 с фреймворком Spring Boot

* Хорошо, потому что предоставляет готовые средства для создания REST API и маршрутизации HTTP-запросов.
* Хорошо, потому что поддерживает интеграцию с PostgreSQL и другими средствами хранения данных.
* Хорошо, потому что предоставляет инструменты для реализации бизнес-логики, проверки входных данных и обработки ошибок.
* Хорошо, потому что обладает развитой экосистемой библиотек и документации.
* Нейтрально, потому что требует изучения особенностей Spring Boot и его компонентов.
* Плохо, потому что использование большого количества зависимостей может увеличить потребление ресурсов приложения.

### Java с платформой Jakarta EE

* Хорошо, потому что предоставляет стандартизированные средства для разработки серверных приложений.
* Хорошо, потому что поддерживает создание REST API и работу с базами данных.
* Хорошо, потому что позволяет использовать единые спецификации и стандарты Java EE.
* Нейтрально, потому что для развёртывания может потребоваться настройка совместимого сервера приложений.
* Плохо, потому что настройка окружения и отдельных компонентов может потребовать дополнительных усилий.
* Плохо, потому что выбранный вариант может оказаться избыточным для масштаба CaterFlow.

### Самостоятельная реализация обработки HTTP-запросов

* Хорошо, потому что разработчик получает полный контроль над внутренней реализацией серверной части.
* Хорошо, потому что отсутствует зависимость от конкретного веб-фреймворка.
* Плохо, потому что потребуется самостоятельно реализовать маршрутизацию, обработку запросов и другие базовые механизмы.
* Плохо, потому что увеличивается объём кода и время разработки.
* Плохо, потому что повышается риск ошибок при реализации сетевого взаимодействия и обработки запросов.
* Плохо, потому что данный подход не соответствует ограниченному сроку разработки CaterFlow.
